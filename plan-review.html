Resolved · 21 August 2026

All eleven findings accepted and applied to the plan

The plan document has been revised. Citations stripped, precedence chain inverted with protected preferences carved out, merge semantics scoped to within-layer, type="number" replaced, settings split into simple and detailed modes, roadmap resequenced around a vertical slice, and Tailwind retargeted to v4. Five findings were refined during review — those are marked below.

What holds up

I checked every external claim the document makes. All of them are accurate, which is not typical for a plan of this length.

  • OKWCAG 2.2 SC 2.5.8 — 24×24 CSS px, “subject to exceptions.” Correct, and the plan is right that there are exceptions (spacing, equivalent control, inline, user-agent, essential). It is also right to treat 24px as a legal floor and design well above it.
  • OKSRD 5.2.1 under CC-BY-4.0. Correct. One gap: the license mandates a verbatim attribution string and explicitly forbids adding any other attribution to Wizards. The plan says “include the required attribution” without recording what it is. Put the exact sentence in the repo now, before content lands.
  • OKAPG’s slider warning about touch AT. Near-verbatim and correctly characterised: touch assistive tech must synthesise key events to move a slider, and that convention “may not be fully implemented.” This matters more than the plan realises — see D4.
  • OKThe four preference media features and the caveat that support varies. Accurate. Three more are worth adding: prefers-reduced-transparency, inverted-colors, and scripting.
  • OK“A custom ARIA role is a behavioral promise.” An accurate reading of the first rule of ARIA, and the correct organising principle for a component library.

Two ideas here are genuinely better than standard practice and should survive any revision. Profiles are UI preferences, not diagnoses (§10.1, §23.11) — most “accessibility mode” products get this wrong. And calibration asks about outcomes, not conditions (§13.1): “which text size is easiest to read” instead of “do you have low vision.” Keeping the character profile separate from the accessibility profile (§18) is a real privacy insight, because accessibility settings are health-adjacent data.

Seven places the plan argues against itself

These are not disagreements with the vision. In each case the document states a principle and then, somewhere else, specifies something the principle rules out. The fix is to apply its own rule.

D1

The precedence chain can override a harm-avoidance setting

Fix before coding Applied
§5.4 — Guiding principle The project should not fight accessibility features the platform already provides.
but
§12 — Precedence order browser / OS preference → built-in toolkit defaults → selected profile(s) → user customizations

Read as a cascade — later wins — this puts OS preferences at the bottom of the stack. Toolkit defaults would override the operating system, which is certainly not intended, and a saved profile could quietly re-enable animation for someone whose OS says prefers-reduced-motion: reduce. For a vestibular disorder that is not a preference violation, it is nausea or a migraine.

§12’s merge table patches the single case (reduced motion → OR), but the two mechanisms contradict each other and the document never says which one is authoritative. That ambiguity is the bug — the plan itself demands the result be “deterministic and explainable.”

Suggested resolution

Invert the first two layers and split the safety-relevant preferences out:

toolkit defaults          base layer
  ↓
browser / OS preference   seeds initial values
  ↓
selected profile(s)
  ↓
user customization
  ↓
per-component override

except: reduced-motion, forced-colors and reduced-transparency
may only be relaxed by an explicit, deliberate user action —
never as a side effect of loading a profile.
D2

“Max wins” merging makes adaptations irreversible

Fix in the doc Applied
§5.7 — Guiding principle Accessibility settings should be easy to change and easy to reset. Users should never have to “commit” to a particular profile permanently.
but
§12 — Merge semantics font scale → max  /  spacing scale → max  /  minimum target → max

A user loads “Large Text” at 1.5×, finds it slightly too big, and asks for 1.25×. Under max-merge they cannot have it. The safest-value rule is right for combining two profiles, but wrong when applied to the user’s own explicit adjustment — it turns a starting point into a floor.

Suggested resolution

Scope max-merge to within a layer: when two profiles are active, take the max. The user-customization layer above it sets absolute values that replace, not raise. That preserves both the safety intent and reversibility.

D3

<input type="number"> is the wrong default for this app

Fix before coding Applied
§5.1 — Native first <input type="number"> where appropriate
but
§24.6 — UX pitfall to avoid Tiny +/- controls. Number adjustments are particularly common in a D&D sheet and should have comfortable interaction targets.

The native number input is the tiny +/− control — its spinner arrows are roughly 10×10px and not author-resizable. The GOV.UK Design System dropped type="number" after user testing: scroll-wheel and trackpad gestures silently change the value while a user is scrolling past, and there are zoom and autofill problems on top. Every one of those failure modes is aimed squarely at this project’s users, and this is the single most-used control in the app — HP, six ability scores, every modifier.

Suggested resolution

Use <input type="text" inputmode="numeric"> (inputmode="decimal" where fractions are possible), which still summons the numeric keypad on phones. Pair it with the large explicit stepper buttons the plan already designs in §26.4. Native-first is still the right principle — type="number" is just the one native control that fails it.

D4

The settings screen is built from the one control the plan warns about

Fix before coding Applied
§24.7 — UX pitfall to avoid A slider may be useful, but every critical setting should have a precise non-drag interaction if practical.
but
§16 — Settings UI mockup Text size [slider] · Spacing [slider] · Control size [slider] · Focus visibility [slider]

Four of the seven settings are sliders, and they are the four that matter most. Two compounding problems: the APG warning you already cite means touch AT may not be able to move them at all, and there is a bootstrapping trap the plan doesn’t name — the accessibility settings UI must be operable at the user’s current, worst configuration. Someone who cannot see or hit things accurately is exactly the person who needs to reach these controls, and a drag target is the hardest thing to offer them.

Suggested resolution

Make the primary control a set of named discrete steps — a radio group or large stepper reading Small · Medium · Large · Larger · Largest — with the slider available as an optional secondary refinement. Discrete steps also make the calibration wizard’s output reproducible and easier to describe in an exported profile. Add a rule to §16: the settings panel must remain operable at every setting it can produce, including the extremes.

Refined — as built

Discrete steps trade precision for operability, and for some users that trade is wrong. The plan now ships two modes: simple mode with named steps as the default, and an opt-in detailed mode exposing sliders and numeric inputs over the full range. Every slider in detailed mode carries an adjacent numeric field, so drag is never the only route to a value, and custom values survive a return to simple mode. Best-effort accessibility by default, full control one action away — §24.9 progressive disclosure applied to the settings panel itself.

D5

The roadmap builds the framework first — which §43 forbids

Fix before coding Applied
§43 — Final project philosophy Do not turn it into a giant framework before there is a real application proving the need for the abstractions.
but
§36 — Proposed roadmap Phase 1 primitives → Phase 2 tokens and profiles → Phase 3 calibration → Phase 4 D&D character sheet

Eleven components, a token system, six profiles and a seven-step calibration wizard all get designed and frozen before a single person sits at a table with the thing. Every abstraction in Phases 1–3 is built without the feedback that would tell you whether it is the right abstraction — precisely the failure §43 names. The friend this project exists for waits three phases to get anything.

It is also a volunteer-retention problem. “Help me build a component library” recruits differently from “help me get my friend playing D&D again,” and the second is the one that’s true.

Suggested resolution — a vertical slice first

Reorder so a usable sheet exists in weeks, then generalise from what it taught you. See the sequence at the end of this review.

D6

The HP controls invite mistaps and offer no undo

Fix in the doc Applied
§8.3 — Component contract [Every interactive target should] tolerate accidental taps where practical.
but
§26.4 — Resource editing [ -10 ] [ -5 ] [ -1 ]  /  [ +1 ] [ +5 ] [ +10 ]

Six adjacent buttons, deliberately large, operated one-handed under time pressure by users with motor impairments — mistaps are not an edge case, they are the expected case. Nothing in the plan provides undo for anything, and the “tolerate accidental taps” requirement is never cashed out into a mechanism.

Suggested resolution

Add a persistent last-change line directly under the HP value: “−5 → 29 HP  [Undo]”. This does three jobs at once — it satisfies §8.3, it gives the change a text representation for screen readers, and it puts the feedback adjacent to the control that caused it, which is what D8 needs.

Refined — as built

Generalised rather than special-cased. The plan now defines an updatable element in a new §8.7 of the component contract: any component that mutates a value the user cares about must be capable of rendering its change as text adjacent to the control, with that display profile-configurable, and must offer a route back. This covers spell slots, proficiency toggles, ability scores and conditions, not just hit points.

D7

Menu is listed as a v1 primitive

Cheap Applied
§23.6 — Known difficult problem Custom sliders, comboboxes, draggable elements, and interactive grids carry a significant accessibility burden.
but
§7.1 — Initial primitives Dialog · Disclosure · Popover · Menu

The APG menu pattern models desktop application menus and needs roving tabindex, type-ahead and full arrow-key semantics. It belongs on §23.6’s list, and it is one of the most frequently mis-implemented patterns on the web — applied to ordinary navigation it makes screen-reader output worse than a plain list of links would have been. It is already absent from the §42 milestone; §7.1 just hasn’t been trimmed to match.

Suggested resolution

Drop Menu from v1 and build Popover on the native popover attribute rather than from scratch. Nothing in the character sheet or the settings panel needs a true menu widget.

Four things that aren’t in the plan at all

Unlike the contradictions above, these are absences. The first is the most consequential, and it is directly relevant to the friend this project is for.

D8

Screen magnification is never mentioned

Fix before coding Applied

The plan covers browser zoom and text scaling thoroughly — 200%, 400%, reflow, §23.7’s list of layout traps. But magnifier software (ZoomText, macOS Zoom, Android magnification, commonly 2×–16×) is a different mechanism: the layout doesn’t reflow at all. The user pans a small window over an unchanged page and may see a fifth of the screen at a time. Every reflow fix in §23.7 does nothing for them.

Three things in the current design break under it, and all three are load-bearing:

  • A dice result announced in a live region placed away from the button that triggered it lands outside the magnified viewport. The user taps Roll and sees nothing happen.
  • §16’s [ Preview ] sits below the whole settings stack — the user cannot see the control and its effect simultaneously, which defeats the point of a preview.
  • Any toast or banner in a page corner is simply invisible.
Suggested resolution

Adopt a stated design rule: feedback appears adjacent to the control that caused it. Roll results render next to the roll button, not only in a status bar. The settings preview updates a sample control sitting inline beside each setting. Then add magnifier passes to §21.2 and a “visible within a 1/5-viewport window” check to §37. This is cheap if decided now and expensive to retrofit, because it constrains layout.

D9

Local-only storage puts calibration one cache-clear from gone

Fix in the doc Applied

§17’s local-first stance is right, and §18’s privacy reasoning is genuinely good. But a calibrated profile is the output of a seven-step wizard, and localStorage is evictable: Safari caps script-written storage for non-installed sites, private browsing discards it, “clear site data” takes it, and IndexedDB can be evicted under storage pressure. The failure mode is nasty and specific — the user loses the settings that made the app legible, so they must now redo calibration in an app they can no longer read comfortably.

Suggested resolution

Three additions, none of which need a server or compromise §18: call navigator.storage.persist() once calibration completes; make export a prompted final step of the wizard rather than a button in a panel; and consider encoding the profile in a URL fragment or QR code so it can move to a new device without an account. Add a durability line to §37’s profile checklist.

Refined — as built

Marked deferred, but the abstraction is reserved now so the decision stays open. Persistence is specified as an interface with interchangeable backends — localStorage, sessionStorage, cookie, IndexedDB, and explicit JSON download/upload — rather than direct calls to any one of them. QR encoding is recorded as a research-backlog item, since it needs tooling that does not exist yet.

D10

§41 asks how to test palettes scientifically; nothing answers it

Fix in the doc Applied

§24.2 correctly says high contrast is not black-and-white, and §41 asks the right open question — “How do we test color palettes scientifically rather than by visual intuition?” — but no section supplies a method. The gap has a structural cause worth naming: contrast is a function of colour and size and weight, while §9 puts colour, typography and size in three separate token groups that are never evaluated together.

Suggested resolution

Treat a contrast token as a triple of (foreground, background, minimum size/weight) rather than a colour pair, and add a CI check that walks the full matrix of colour tokens × type tokens × every shipped profile. That matrix is also the honest answer to whether a profile combination is safe — it is a computation, not a judgement call. WCAG 2.x ratios are the practical baseline; treat APCA as a research-backlog item in §39, not a v1 commitment, since WCAG 3 is nowhere near stable.

Refined — as built

The computed matrix is written into the plan as a floor, not the setting. Automated validation establishes that a palette is not broken; it does not establish that a palette is comfortable, and those are different questions. Explicit user configuration of contrast stays a first-class feature precisely so the project can calibrate against real preferences with people who have relevant lived experience, rather than shipping whatever a ratio calculation permits.

D11

The §22 test matrix is more than a volunteer project can maintain

Cheap Applied

Twelve conditions applied to roughly twenty-five components is around 300 visual-regression baselines, every one of which needs re-approving whenever a token changes. On a volunteer project that will be abandoned within two months, and a half-maintained snapshot suite is worse than none because it trains people to click through failures.

Suggested resolution

Split the matrix by cost. Run the cheap assertions — computed target size, contrast, accessible name, no horizontal scroll at 320px — programmatically across the full matrix, since those are numbers and not screenshots. Reserve visual snapshots for a named handful of high-risk pairs (Dialog × 400% zoom, the HP control × large-targets, the settings panel × forced-colors). Also add SC 1.4.12 text-spacing and SC 1.4.10 320px reflow to §37 as explicit checkboxes — §8.5 implies both but the Definition of Done omits them, and only what’s on the checklist gets done.

Refined — as built

§22 is now sorted into three cost tiers: computed assertions run exhaustively on every commit, visual snapshots restricted to five named high-risk pairs each carrying a written justification, and manual/AT testing per release. A new §22.4 states plainly that tier 3 exceeds volunteer capacity at the full scope described, and names the two honest responses — reduce scope, or secure dedicated resourcing. Until one is settled, accessibility claims stay scoped to what has actually been tested.

The one structural change worth making

If you act on nothing else here, act on D5. This is a concrete replacement for Phases 1–4 that keeps every deliverable in the plan and only changes what order they arrive in. The steps are numbered because the order is the point.

  1. One screen, on a real phone, with your friend

    HP with steppers and undo, and one skill row that rolls. Three components, hard-coded values, no profiles, no tokens, no build system decisions you can’t reverse. The goal is a session at an actual table — and the questions it answers (how big is big enough, does the roll result get noticed, what did they reach for that wasn’t there) are the ones every later abstraction depends on.

  2. Extract tokens from what that screen needed

    You now know which values actually varied for a real person, which is a much better basis for §9’s token list than enumerating categories up front. Everything that didn’t vary stays hard-coded until something makes it vary.

  3. Fill out the sheet with the components it demands

    Ability scores, saves, skills, combat stats. Build a primitive when the sheet needs one, not because §7.1 lists it. Components that never get demanded were never needed — that is the §43 test working as designed.

  4. Generalise the settings into the profile system

    Now do §12 properly, with the corrected precedence from D1 — and with real profiles to test the merge rules against rather than hypothetical ones.

  5. Calibration last

    The wizard produces a profile, so it cannot be designed before the profile format has been proven. Building it earlier means building it twice.

This reaches the same place as the existing Phases 0–6 and delivers something usable at step 1 instead of step 4. It also changes the pitch to volunteers from “help build a component library” to “help get people playing,” which is both more accurate and easier to say yes to.
